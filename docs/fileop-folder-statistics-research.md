# FileOP folder statistics research

Research date: November 10, 2026. Scope: public File Pilot material, read-only inspection of the installed executable's PE import table and user configuration keys, the observations supplied with this request, and the current FileOP working tree. This is architecture research, not a reproduction of File Pilot code. No File Pilot scan was instrumented in this session: Process Monitor was unavailable, and no controlled UI trace was captured. Consequently, several internals remain unknown.

## 1. File Pilot: established behavior and evidence

| Finding | Evidence and limit |
| --- | --- |
| Automatic folder statistics are controlled separately for SSD, HDD and network locations. | Supplied UI observations; the installed `FPilot-Config.json` has `CalcFolderSizes`, `CalcFolderSizesSSD`, `CalcFolderSizesHDD` and `CalcFolderSizesNetwork`, all `true` at inspection time. The [v0.6.4 starlog](https://filepilot.tech/starlog/2025-12-22-v0.6.4) explicitly records network settings being added. |
| A VM C: drive needed HDD scanning enabled; results then appeared within several seconds. | Supplied runtime observation. This establishes File Pilot's **classification outcome on that VM**, not the exact probe or an HDD device. Virtual storage may report an unknown or seek-penalty class. |
| Details has Folders, Files and Size columns; large directories populated without visibly blocking the interface; some results show `--`. | Supplied runtime observation. It does not establish exact completion time, I/O count, whether displayed values are complete, or the meaning of `--`. |
| Folder statistics can arrive after a view and trigger a sort. | The [v0.6.4 starlog](https://filepilot.tech/starlog/2025-12-22-v0.6.4) says it fixed automatic resorting when new folder statistics are calculated. This supports asynchronous delivery but not a particular worker count or partial-update cadence. |
| File Pilot has background directory monitoring and a file path cache. | The same starlog discusses its directory watcher and stale file path cache. Neither statement identifies a folder-statistics cache or its invalidation policy. The [v0.8.5 starlog](https://filepilot.tech/starlog) also records races involving folder statistics and directory-size threading, consistent with asynchronous work. |

The installed `FPilot.exe` is 2,585,680 bytes (file timestamp November 10, 2026). Read-only PE import inspection found `FindFirstFileExW`, `FindNextFileW`, `FindFirstFileW`, `ReadDirectoryChangesW`, `GetDriveTypeW`, `GetVolumeInformationW`, `DeviceIoControl`, and Windows thread-pool imports. These are **capabilities of the executable**, not proof of which function computes folder totals. In particular, `DeviceIoControl` could support several unrelated operations and does not establish USN, MFT, or raw-volume scanning. No protected code was disassembled or extracted.

The publisher's [roadmap](https://filepilot.tech/roadmap) lists direct NTFS file-table indexing as a **future** feature. The [download FAQ](https://filepilot.tech/download) describes filesystem indexing as platform-specific, but does not specify the current folder-statistics algorithm. Taken together, ordinary directory enumeration plus a responsive worker/cache design is plausible; a current MFT fast path cannot be confirmed from these sources. Standard `FindFirstFileExW` returns entry metadata while enumerating, and its large-fetch option can reduce enumeration round trips, especially on high-latency media ([Microsoft documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw), [Microsoft engineering note](https://devblogs.microsoft.com/oldnewthing/20131024-00/?p=2843)).

## 2. FileOP today

The present implementation is an **explicit selected-total command**. `crates/atlas-ui/src/app/context_info.rs` takes selected paths, or the current directory when selection is empty, and starts one `spawn_blocking` job. Pressing the command during a job requests cancellation. Only one `SizeJob` is held globally; its report is associated with a tab, path set, listing version and generation. `BgResult::FolderSizeUpdate` updates the context pill, not Details rows (`crates/atlas-ui/src/app/bg.rs`).

`crates/atlas-core/src/fs/folder_size.rs` walks roots serially with `std::fs::read_dir`, calling `symlink_metadata` for **each entry**, and sums logical file lengths. It publishes a cloned cumulative `SizeReport` at most every 150 ms and once at completion. The report has bytes, files, skipped, errors, first error, cancelled and done; it has **no folder count or per-directory results** (`crates/atlas-model/src/folder_size.rs`). It deduplicates overlapping selected roots, avoids reparse/offline/recall entries, and limits open iterators/tree depth to 256. It calls a private/vault exclusion predicate for each visited path. A skipped count therefore includes intentionally omitted reparse points, offline/recall entries, private paths, non-file/non-directory entries, and subtrees past the depth cap. It is an **entry count**, not a count of omitted descendants. Failed metadata/enumeration increments errors instead. Windows system churn exclusions in `fs/scan_policy.rs` are used for automatic list/watch behavior; this size scanner's exclusion closure is specifically vault/private policy.

Likely latency contributors are repeated per-entry metadata calls after enumeration, serial traversal of all selected roots, per-path private checks, and no reuse of a previously scanned subtree. These are source-based bottleneck hypotheses, not a measured FileOP/File Pilot speed ratio. There is no explicit file-count, byte-count, elapsed-time, per-volume I/O, or network budget. Cooperative cancellation checks occur between entries, so an individual blocking network call can still delay cancellation. The 256-level cap bounds handles but yields partial results. Existing `read_dir` and `symlink_metadata` scan file metadata only; no file contents are read.

The current snapshot lives in one in-memory `SizeJob`, with no shared subtree cache or persistence. UI marks a completed result stale when the current listing version changes or after 60 seconds; pressing Calculate always rescans. The normal `watch_path` is non-recursive (`crates/atlas-core/src/fs/watcher.rs`), so a nested change may not increment the parent listing version. The 60-second rule limits staleness in the pill but is not reliable recursive invalidation. Navigation to another path makes `folder_size_text` stop showing the result; it does **not itself cancel** the worker. The worker is cancelled when the app drops, a scan is toggled, or its tab disappears during context sync.

Details currently has fixed Name plus Size, Modified and Type metadata columns (`crates/atlas-ui/src/app.rs`, `ui/views/details_dg.rs`, `ui/views/details_header_element.rs`). The column layout, widths, order persistence, animation and row painting assume three metadata columns. `entry_display_size` returns blank for directories, and `SortColumn::Size` compares `FileEntry::size()`; neither reads the size report. `FolderColumns` stores four width ratios and a three-key order. Resizing/reordering already works for the existing columns, but adding Folders/Files requires migration to a variable-length column list, a visibility set, and careful narrow-pane projection. The current FileEntry has a compact 64-byte bound; calculated aggregates should live in a separate path/identity keyed store rather than enlarging every row.

## 3. Recommended design

### Semantics and model

Define one contract before implementation: for each directory row, `Folders` counts descendant directories (excluding the row itself), `Files` counts descendant regular files, and `Size` sums their logical byte lengths. An empty directory is complete `0 / 0 / 0`; unavailable data is never shown as zero. Reparse points, junctions, symbolic links, offline placeholders and private vault paths are not traversed by default. Expose their omission as partial with reason counts. Count file hard links by directory entry (consistent with logical tree traversal) and document that logical bytes can double-count hard-linked content. Decide separately how archive/virtual rows present these fields; initially use unavailable.

Use a `FolderStats` record keyed by canonical volume identity plus a path or stable file ID, with `bytes`, `files`, `folders`, `state` (`Pending`, `Partial`, `Complete`, `Stale`, `Cancelled`, `Error`, `Disabled`), reason counts, generation, scan time, and source-change epoch. Keep the aggregate outside `FileEntry`. Publish per-directory deltas and completion events. Each parent aggregate receives its direct files plus finalized child aggregate, allowing one traversal to populate multiple visible folder rows and their descendants without repeatedly scanning shared subtrees. Treat overflow with checked/saturating arithmetic plus an explicit overflow state.

### Scheduler and scanning

- Master **Calculate Folder Sizes** toggle controls automatic requests; SSDs, HDDs and Network Locations gates apply only when master is on. Manual Folder Size always works for supported native paths, even when automatic gates are off, and uses the same scheduler/cache with higher priority.
- Do no scan during startup. After a listing is visible, enqueue visible directory rows first, then nearby rows. Debounce rapid navigation. A new pane generation makes old row updates ineligible; cancel work with no subscribers. A shared subtree job may continue for another subscriber or cache reuse. Suppress duplicate and ancestor/descendant overlapping jobs.
- Begin with native Win32 directory enumeration on Windows, using metadata returned by enumeration rather than a second metadata call for every entry. `FindFirstFileExW` with `FindExInfoBasic`/large-fetch should be benchmarked and used only where it improves full traversal. Retain portable `read_dir` fallback. Build a post-order aggregate in one scan and publish bounded batches (for example every 50–150 ms or a bounded number of entries). Prioritize UI notifications for visible rows; batch resorting to avoid row churn.
- Use a fixed, small worker pool and per-volume permits: initial policy could be two concurrent jobs on SSD, one on HDD and one on a network share, with an overall cap of four. These are **starting values for benchmarks**, not File Pilot measurements. Bound queued requests and cache bytes; let unviewed automatic work expire. Add network elapsed-time and entry budgets and a clear partial/paused state. Do not recursively auto-scan a network root or unknown device by default. A manual request can opt into a scoped scan with cancel/progress.
- Detect UNC and mapped remote paths first. Resolve volume/root and query drive type; distinguish SSD/HDD with a supported seek-penalty/storage query where available. Treat virtual, removable, mixed, unsupported and unknown responses conservatively as HDD-like for policy, with a visible reason and optional override. Cache the classification per volume and re-evaluate on remount/device change. Do not equate `DRIVE_FIXED` with SSD.

### Cache and invalidation

Use a bounded in-memory LRU initially. Cache complete and partial results separately, with volume identity, path/file identity, scan generation and a freshness epoch. Reuse a valid child aggregate for both browsing and manual requests. Make persistence a later option only after correctness and invalidation are proven; never block startup loading it. A TTL alone is a fallback, not correctness.

On FileOP-owned create/delete/move/rename/write operations, invalidate affected path plus known ancestors immediately. Feed directory watcher events into the same invalidation service. A watcher on only the displayed parent is insufficient for nested descendants: use a bounded recursive watch for active roots where practical, or mark descendant cache entries stale on navigation/revisit and rescan. On watcher overflow, disconnect, rename ambiguity, volume remount, or network reconnect, invalidate the whole affected scope. USN journal tracking is a possible later local-NTFS optimization, but adds volume/permission and recovery complexity and is not required for the first implementation. [Microsoft's watcher documentation](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-readdirectorychangesw) explicitly describes subtree watching and overflow/rescan conditions.

### Details integration

Extend the existing Details column preference model to a versioned, variable-length ordered set: mandatory Name, with Size, Folders, Files, Modified and Type independently visible. Preserve old three-column preferences through migration. Each optional column should support visibility, width and order; Size remains the current file size for files and shows calculated directory size when available. Folders/Files show recursive counts for folders and a deliberate blank or dash for files. Header sorting uses the same aggregate snapshot as painting; sort known complete values numerically, place pending/partial/unavailable values in a defined stable group, tie-break by name, and throttle automatic resort to avoid jumping rows. If partial values are sortable, label them as lower bounds rather than exact totals. Make the active DG path and fallback canvas path use one shared column/row specification.

## 4. Expected performance and tradeoffs

First cold scan still costs at least a directory-entry traversal for a portable implementation: time is approximately proportional to entries plus I/O latency. Avoiding one extra metadata query per entry and reusing shared aggregates should materially improve FileOP's cold and especially warm behavior, but a numeric speedup is not defensible without a fixture benchmark. SSDs often tolerate modest parallelism; HDDs can regress from seek contention; network shares are dominated by round trips and can stall indefinitely without policy limits. Publishing partial values improves perceived latency but requires explicit state and stable sorting. A cache makes revisits fast but increases memory use and stale-result risk; aggressive recursive watching adds handles and failure modes. Native enumeration provides broad filesystem support, while a direct-MFT/USN fast path would be NTFS-specific and far more complex.

## 5. Phased implementation plan

1. **Semantics and measurements:** build disposable fixtures for nested totals, empty trees, junctions, symlinks, hard links, denied paths, offline placeholders and mutation. Record cold/warm scan time, entries/sec, I/O operations, CPU, handles, UI frame latency and cancellation latency on SSD/HDD/VM/network where available. Confirm File Pilot's recursive count and error display using only fixtures.
2. **Core aggregation:** add `FolderStats` and a single-pass, post-order scanner with native enumeration on Windows, explicit partial states and progress batching. Benchmark against the current `read_dir` path; retain the faster safe path per filesystem. Keep manual command behavior intact.
3. **Scheduler and cache:** add bounded per-volume jobs, deduplication, generation/cancellation, LRU and invalidation hooks. Gate automatic work by device class and defer it until listing is displayed.
4. **Details and settings:** migrate column preferences; add Folders/Files, calculated Size, resizing/visibility/reordering/sorting; add master and medium toggles and clear pending/partial UI.
5. **Hardening:** watcher overflow/remount handling, slow network timeouts/budgets, profiling, accessibility/localization, and optional persistence only if cold revisit cost justifies it.

## 6. Safety risks and required tests

- **Cycles and escape:** junction/symlink loops, mount points and reparse tags must neither recurse indefinitely nor cross into excluded/private/network areas. Test disposable cycles and links to another disposable tree.
- **Completeness:** denied directory, deleted file during enumeration, offline cloud placeholder, depth/entry/time budget, overflow, cancelled job and watcher failure must produce partial/error states, never a complete-looking zero. Test races while mutating a disposable tree.
- **Invalidation:** nested file-size change, rename/move between cached siblings, deletion, watcher overflow, drive remount and reconnect must invalidate every affected ancestor. Test both app-owned and external changes.
- **Responsiveness and resources:** verify bounded workers, queue, handles, cache memory, network I/O, startup time, frame time and cancellation latency. Run a slow-share simulation or controlled share; no production user-data scan is needed.
- **UI correctness:** test column migration, visibility, widths, reorder and numeric sorting under pending-to-complete transitions, narrow panes and multiple tabs; check that stale generations cannot paint or reorder the current view.

## 7. Remaining unknowns

File Pilot's exact statistics algorithm; use of `FindFirstFileExW` vs another enumeration path for totals; worker count and per-device limits; whether single-folder totals update progressively; cache persistence and precise invalidation; navigation cancellation; exact SSD/HDD probe and VM fallback; handling of reparse points, denied folders and `--`; whether counts are recursive and whether the directory itself is counted; cold/warm timings and UI frame metrics. Resolve these with the bounded fixture and trace above, not by inferring internals from import names or visual speed.
